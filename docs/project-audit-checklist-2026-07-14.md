# FLVXR2 项目审计与测试清单

审计日期：2026-07-14
审计对象：`D:\Data\RSSQ\flvxt2` 及测试服务器 `10.0.0.142`
代码基线：`main` / `3.0.27` / `26b35778`
测试服务器版本：容器镜像 `3.0.24`，Agent 服务在线

## 1. 结论

当前版本可以完成编译并启动主要服务，但**不建议直接作为正式商业版本发布**。审计确认存在以下四类关键问题：

1. 普通用户可以调用多项管理员接口，包括面板升级、授权配置、节点分组和标签管理等。
2. 密码仍使用无盐 MD5 保存；公开配置接口没有字段白名单，存在泄露授权密钥和其他配置秘密的条件。
3. 新增的策略防火墙尚未形成可靠闭环：绑定范围没有真正生效、Mihomo 未运行也会显示已应用、重启后规则可能消失但状态仍显示成功。
4. 后端全量测试存在 13 个顶层失败项，覆盖备份恢复、旧数据库迁移、面板共享、连接地址和事务回滚等重要路径。

建议先完成 P0 和 P1 清单，再进行正式发布和镜像同步。

### 项目状态整理

- 项目约 1025 个文件，主体分为 `go-backend`、`go-gost`、`go-gost/x`、`vite-frontend`、`scripts`、`deploy` 和 `docs`。
- 当前工作区包含尚未提交的策略防火墙开发内容，因此它不是一个可直接打标签发布的干净基线。
- 当前 Git 标签为 `3.0.27`，测试服务器仍运行 `3.0.24`，黑盒结果不能替代对 `3.0.27` 最终产物的发布验收。
- 仓库同时保留旧版和新版更新接口，发布、容器更新、Agent 更新之间尚未形成单一版本源。
- Git 已跟踪约 79 MB 编译后二进制；应将源代码、可复现构建和 Release 资产明确分层。

| [ ] | 策略防火墙绑定范围未生效 | Agent 解析了节点、隧道、角色、接口、端口等字段，但生成规则时没有使用；CIDR 规则被同时写入 INPUT、FORWARD、OUTPUT | 原本只绑定单个入口或隧道的策略可能影响整台服务器流量，存在断网风险 |
| [ ] | 策略引擎存在假成功 | 只生成 Mihomo YAML、没有 Mihomo 进程时仍可记录为 `applied`；测试服务器没有 Mihomo 服务 | UI 显示已防护，实际流量没有执行域名策略 |

## 5. 策略防火墙缺失能力

- [ ] 将 provider 规则解析为稳定、可版本化的中间模型，而非只保存原始 YAML 和计数。
- [ ] 根据绑定对象编译不同作用域：节点入口、节点出口、隧道入口、隧道出口、转发规则。
- [ ] 使用独立的 nftables 表、链和集合，避免影响 FLVX 原有 DNAT/转发规则。
- [ ] 为每个部署生成唯一注释和句柄，支持精准删除和替换。
- [ ] 禁止把局部 `allow` 规则无条件插入全局链首部，防止绕过其他防火墙策略。
- [ ] Mihomo Sidecar 需要正式的安装、进程托管、健康检查、透明转发和故障回退流程。
- [ ] 没有代理出站时，只允许 `DIRECT`/`REJECT` 类动作；代理动作必须显式配置出口。
- [ ] Agent 启动时从面板或本地期望状态重放规则，并与内核实际状态对账。
- [ ] 下发、更新、删除采用两阶段处理：先准备和验证，再原子切换；失败自动回滚。
- [ ] 状态接口返回真实执行状态、最后错误、规则数量、引擎进程状态和内核句柄。
- [ ] provider 下载需要超时、大小上限、内容类型校验、缓存、校验和及失败保留旧版本。
- [ ] 增加最小化网络命名空间集成测试，验证入口/出口方向和不串线行为。

## 6. 建议修复顺序

### 第一阶段：立即封堵

1. 建立集中式路由权限表，默认所有管理接口仅管理员可访问；为每组路由增加普通用户 403 合同测试。
2. 立即保护升级、授权、计费、节点分组和标签接口；撤销 `/panel/upgrade` 普通用户访问能力。
3. `license/info` 永不返回 `license_key`、`hmac_key`；公开配置接口改为严格字段白名单。
4. JWT 密钥为空或长度不足时拒绝启动，而不是仅打印警告。
5. 暂时把策略防火墙标记为预览功能，禁止在未完成作用域编译和状态校准前用于生产流量。

### 第二阶段：修复数据与运行态

1. 将密码升级到 Argon2id 或 bcrypt；登录成功时透明迁移旧 MD5，设置迁移截止版本。
2. 修复备份恢复、旧数据库迁移、connectIp、面板共享和限速回滚测试。
3. 修复 `ForwardRecord` 查询实际表名，恢复 nftables 域名转发刷新。
4. 完成策略规则的精确作用域、启动重放、删除清理、健康检查和失败回滚。
5. 合并两套升级接口，使用固定版本资产和校验和，禁止执行漂移的 main 分支脚本。

### 第三阶段：发布工程加固

1. CORS 改为明确允许列表，并减少允许的方法和请求头。
2. 增加登录限流、失败审计和短期账号/IP 退避。
3. 升级 `form-data`、`postcss`、`react-router`/`react-router-dom` 到已修复版本。
4. CI 必须执行后端全量测试、Agent 测试、前端 build/lint、依赖审计和安装脚本检查。
5. 发布流水线验证 SHA256；从 Git 移除已编译二进制，Release 资产由可复现构建生成。
6. 补齐 Nginx 安全响应头，并对前端做路由级拆包。
